# 投研信息流与判断过程数字化落地计划

## 1. 推荐落地方案

第一阶段建议采用 V1-lite：

```text
本地生成结果
-> 上传到阿里云静态托管
-> Channel 推送摘要和链接
```

不建议第一阶段直接做完整云端动态系统。原因是当前最重要的是验证数据和模型是否有价值，而不是先投入复杂后端、数据库和管理后台。

## 2. 架构形态

### 本地电脑负责

1. 定时拉取微信 API。
2. 清洗消息和过滤噪声。
3. 做消息分类。
4. 抽取标准化推荐。
5. 生成今日推荐池。
6. 生成推荐人排行榜。
7. 生成静态 HTML/JSON/PDF。
8. 上传结果到阿里云。
9. 推送 Channel 消息。

### 阿里云负责

1. Nginx 静态页面托管。
2. 对外提供手机可访问链接。
3. 简单访问保护。

云上第一阶段不需要：

1. 动态后端服务。
2. 数据库。
3. 复杂登录系统。
4. 管理后台。

## 3. 数据流

```text
微信 API / 其他数据源
-> 本地定时脚本
-> 本地 JSON/SQLite
-> 消息分类与推荐抽取
-> 核心算法模型
-> 生成静态页面
-> rsync/scp 上传阿里云
-> Channel 推送链接
-> 老板手机打开 H5
```

## 4. 核心算法模型

这一环节是系统的核心，不是简单把消息展示出来，而是把原始投研消息和老板的判断过程转成可沉淀、可验证、可复盘的数据资产。

### 4.1 消息分类模型

先判断每条消息属于哪一类：

| 类型 | 处理方式 |
| --- | --- |
| 有效推荐 | 进入推荐抽取和回测 |
| 研究观点 | 进入行业/板块热度跟踪 |
| 会议/活动/调研通知 | 归档，不作为交易信号 |
| 工具/服务信息 | 归档或过滤 |
| 私人/无关噪声 | 过滤 |

### 4.2 推荐抽取模型

从有效推荐里抽取标准字段：

| 字段 | 说明 |
| --- | --- |
| 推荐人 | 谁发的消息 |
| 推荐标的 | 股票名称、代码、市场 |
| 推荐动作 | 关注、买入、加仓、减仓、卖出 |
| 推荐强度 | 高、中、低 |
| 推荐周期 | 日内、短线、波段、中线 |
| 推荐理由 | 业绩、题材、政策、资金、技术形态等 |
| 风险信息 | 止损、回撤、追高风险等 |

### 4.3 标的识别模型

解决“消息里提到的公司/股票到底是哪一个标的”的问题。

能力包括：

1. 股票名称识别。
2. 股票代码匹配。
3. A股、港股、美股市场区分。
4. 行业和题材归类。
5. 多标的消息拆分。

### 4.4 回测评价模型

把推荐和后续行情表现关联起来：

| 指标 | 说明 |
| --- | --- |
| 1日收益 | 推荐后 1 个交易日表现 |
| 3日收益 | 推荐后 3 个交易日表现 |
| 5日收益 | 推荐后 5 个交易日表现 |
| 10日收益 | 推荐后 10 个交易日表现 |
| 20日收益 | 推荐后 20 个交易日表现 |
| 最大回撤 | 跟踪周期内最大亏损 |
| 是否命中 | 是否达到预设收益或跑赢基准 |
| 是否追高 | 推荐时是否已经处于短期高位 |

### 4.5 推荐人评分模型

形成推荐人画像和排行榜：

| 指标 | 说明 |
| --- | --- |
| 推荐次数 | 有效样本量 |
| 胜率 | 多周期命中比例 |
| 平均收益 | 推荐后的平均涨跌幅 |
| 盈亏比 | 平均盈利 / 平均亏损 |
| 最大回撤 | 推荐风险 |
| 擅长板块 | 表现较好的行业/题材 |
| 擅长周期 | 1日、3日、5日、10日、20日哪个周期更有效 |
| 稳定性 | 不同行情下表现是否稳定 |

### 4.6 信号排序模型

最终给今日推荐池排序：

```text
信号强度
= 推荐人历史表现
+ 多人/多来源共振
+ 推荐内容明确度
+ 标的近期表现
- 追高风险
- 样本不足惩罚
```

这个模型决定老板打开页面后，哪些标的排在前面。

### 4.7 观点演变模型

这部分用于记录同一推荐人围绕同一标的或主题的前后变化。

典型变化：

| 变化类型 | 说明 |
| --- | --- |
| new | 首次提出 |
| reinforce | 持续强化 |
| supplement | 补充证据 |
| revise | 修正观点 |
| reverse | 观点反转 |
| withdraw | 撤回/否定 |

建议字段：

| 字段 | 说明 |
| --- | --- |
| opinion_id | 同一观点链 ID |
| opinion_version | 同一观点的第几次更新 |
| topic_key | 标的/主题归并 key |
| stance | bullish / bearish / neutral / mixed |
| update_type | new / reinforce / supplement / revise / reverse / withdraw |
| previous_opinion_id | 上一条观点 |
| boss_rule_tag | 老板后续沉淀的专业判断标签 |

这部分后续需要老板提供专业规则，例如什么叫“持续强化”、什么叫“风险撤退”、什么叫“事后找补”、什么叫“逻辑兑现”。

### 4.8 第一版实现方式

第一版不必追求复杂机器学习，可以采用：

```text
规则判断 + LLM 结构化抽取 + 观点链归并 + 行情回测统计
```

先让结果可解释、可追溯，再逐步优化评分权重。

## 5. 阿里云部署目录

建议目录：

```text
/var/www/stock-news/
  latest/
    index.html              # 今日 AI 简报
    recommendations.html    # 今日推荐池
    senders.html            # 推荐人排行榜
    data.json               # 页面数据
    report.pdf              # 日报/周报，可选
  runs/
    2026-05-22-0930/
      index.html
      recommendations.html
      senders.html
      data.json
```

老板日常访问：

```text
http://阿里云IP/stock-news/latest/index.html
http://阿里云IP/stock-news/latest/recommendations.html
http://阿里云IP/stock-news/latest/senders.html
```

如果后续有域名，可以升级为：

```text
https://domain.com/stock-news/latest/
```

## 6. Channel 推送形态

Channel 中推送摘要和链接：

```text
【今日推荐简报】
重点观察：3 只
高胜率推荐人动态：5 条
多人共振：2 只
风险提示：1 条

今日推荐池：
http://阿里云IP/stock-news/latest/recommendations.html

推荐人排行榜：
http://阿里云IP/stock-news/latest/senders.html
```

## 7. 访问安全

页面中可能包含聊天原文、推荐人名称和投研信息，不能裸奔公网。

第一阶段建议至少做一种保护：

1. Nginx Basic Auth。
2. 长随机路径。
3. 访问 token。
4. 内网/VPN。
5. 后续接飞书鉴权。

最小可行方案：

```text
Nginx Basic Auth + 长随机路径
```

例如：

```text
/var/www/stock-news-mf-8f3a91/latest/
```

## 9. 服务器要求

已有阿里云 IP 的情况下，服务器要求很低：

```text
1核2G 或 2核2G
系统盘 40G
Nginx
无需数据库
无需后端服务
```

新增成本：

```text
已有 ECS：基本无新增成本
新买 ECS：几十元/月起
域名：可选
HTTPS：有域名后再配置更合适
```

## 10. 阶段计划

### 第 0 阶段：准备

目标：确认服务器和推送方式。

任务：

1. 确认阿里云 IP、SSH 用户、部署目录。
2. 确认是否已有 Nginx。
3. 确认 Channel 推送方式：飞书机器人、企业微信机器人或其他。
4. 确认是否需要域名和 HTTPS。

### 第 1 阶段：本地数据验证

目标：跑通数据源。

任务：

1. 拉取个人消息和个人群 API。
2. 按时间窗口增量拉取。
3. 保存原始消息。
4. 输出数据质量报告。
5. 确认消息分类标准。

交付：

1. API 探查脚本。
2. 原始消息样本。
3. API 协议文档。

### 第 2 阶段：核心算法模型

目标：把原始消息变成可验证、可排序、可复盘的信息流和观点链。

任务：

1. 消息分类。
2. 推荐抽取。
3. 标的识别。
4. 推荐标准化。
5. 观点链归并。
6. 推荐人评分。
7. 信号排序。

交付：

1. 标准化推荐数据。
2. 观点链数据。
3. 推荐人评分数据。
4. 今日推荐池排序结果。
5. 可追溯的原文关联。

### 第 3 阶段：静态页面生成

目标：让老板看到第一版效果。

任务：

1. 生成今日 AI 简报页面。
2. 生成今日推荐池页面。
3. 生成推荐人排行榜页面。
4. 支持原文追溯。
5. 生成页面数据 JSON。

交付：

1. `index.html`
2. `recommendations.html`
3. `senders.html`
4. `data.json`

### 第 4 阶段：阿里云托管

目标：手机能打开链接。

任务：

1. 配置 Nginx 静态目录。
2. 配置 Basic Auth。
3. 配置部署目录。
4. 编写上传脚本。
5. 验证手机访问。

交付：

1. 阿里云访问链接。
2. 上传部署脚本。
3. 访问账号和密码。

### 第 5 阶段：Channel 推送

目标：老板不用主动打开系统，也能收到摘要。

任务：

1. 配置机器人 webhook。
2. 生成推送文案。
3. 推送今日简报链接。
4. 推送推荐池和排行榜链接。

交付：

1. Channel 简报推送。
2. 页面链接。

### 第 6 阶段：定时化

目标：形成自动运行。

任务：

1. 本地 crontab 或 launchd 定时执行。
2. 拉取 API。
3. 生成页面。
4. 上传阿里云。
5. 推送 Channel。
6. 记录日志和失败原因。

交付：

1. 定时任务。
2. 日志文件。
3. 失败重试或失败提醒。

## 11. 风险与取舍

### 本地电脑稳定性

如果本地电脑关机、断网或休眠，定时任务会停止。

取舍：

1. 第一阶段可以接受，用于验证。
2. 如果老板认可效果，再把定时任务迁到云服务器。

### 数据安全

页面可能包含聊天原文和推荐人信息。

取舍：

1. 第一阶段用 Basic Auth + 长随机路径。
2. 后续升级飞书鉴权或内网访问。

### 模型准确率

第一版推荐抽取不可能 100% 准确。

取舍：

1. 第一版先明确标注“AI 识别结果，可追溯原文”。
2. 保留人工校正入口作为后续增强。

### 页面不是动态系统

静态页面不能实时交互太复杂。

取舍：

1. 第一阶段足够展示推荐池和排行榜。
2. 后续有价值再升级动态 H5 + 数据库。

## 12. 后续升级路径

如果 V1-lite 被认可，可以升级为：

```text
云端定时任务
-> 云端数据库
-> 动态 API 服务
-> 动态 H5
-> 推荐人长期画像
-> 周报/月报自动复盘
```

升级后可以支持：

1. 实时筛选。
2. 多时间范围查询。
3. 推荐人详情页。
4. 个股共振页。
5. 人工校正。
6. 权限管理。
7. 更完整的行情回测。

## 13. 推荐决策

建议先做 V1-lite：

```text
本地定时任务 + 静态 H5 生成 + 阿里云托管 + Channel 推送
```

它比纯本地更像产品，比完整云系统更轻，能最快让老板看到效果并判断是否继续投入。
